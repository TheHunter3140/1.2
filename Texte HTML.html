PARTIE I — PRÉSENTATION DU PROJET

1. Qu’est-ce que Pal ?

Pal est un assistant d’intelligence artificielle personnel conçu pour fonctionner directement sur iPhone.

Il repose principalement sur l’exécution locale de modèles de langage au format GGUF grâce à llama.cpp.

Ce n’est pas simplement une application permettant de discuter avec un modèle.

La vision est de construire progressivement un véritable environnement d’intelligence artificielle mobile, capable de :

  • Faire fonctionner plusieurs modèles locaux.
  • Analyser des documents et des images.
  • Effectuer des recherches sur Internet.
  • Utiliser des compétences spécialisées (Skills).
  • Conserver une mémoire contrôlée par l’utilisateur.
  • Exécuter des outils.
  • S’adapter aux ressources matérielles disponibles.
  • Fournir des recommandations intelligentes.
  • Gérer plusieurs conversations et personnalités.
  • Fonctionner hors ligne pour les fonctionnalités locales.

Philosophie fondamentale : local-first, modularité, liberté de configuration, confidentialité et performances.

L’utilisateur doit pouvoir contrôler son assistant, ses modèles, ses paramètres, ses données et ses outils.

2. Vision à long terme

Nous voulons que Pal réunisse progressivement les avantages de plusieurs catégories d’applications :

  1. Un assistant conversationnel moderne.
  2. Un gestionnaire de modèles locaux.
  3. Un environnement de raisonnement et d’analyse.
  4. Un système de compétences extensible.
  5. Un moteur de recherche documentaire.
  6. Un assistant connecté à Internet.
  7. Un environnement multimodal.
  8. Un système de diagnostic et d’optimisation matérielle.

Pal doit rester léger, rapide et agréable à utiliser malgré l’augmentation progressive de ses fonctionnalités.

Il ne faut pas confondre richesse fonctionnelle et complexité inutile.

PARTIE II — ENVIRONNEMENT TECHNIQUE

3. Matériel et contraintes

L’appareil de référence est un iPhone XR.

Caractéristiques à prendre en considération :

  • Puce Apple A12 Bionic.
  • Mémoire vive limitée par rapport aux appareils récents.
  • GPU mobile Apple.
  • Neural Engine.
  • Stockage local limité.
  • Gestion agressive de la mémoire par iOS.
  • Absence de contrôle direct sur les fréquences CPU/GPU.
  • Absence de possibilité de forcer un véritable mode basse consommation matériel depuis une application tierce.

Version iOS de référence : 18.7.9.

L’application doit privilégier les optimisations réellement compatibles avec les API iOS.

Contraintes impératives

  • Éviter les allocations mémoire inutiles.
  • Éviter les copies de modèles.
  • Libérer les ressources inutilisées.
  • Éviter les chargements simultanés excessifs.
  • Préserver la fluidité de l’interface.
  • Éviter les blocages du thread principal.
  • Prévoir les interruptions et la suspension de l’application.
  • Ne jamais supposer qu’une capacité matérielle est disponible sans la vérifier.

9. Nettoyage des messages personnalisés

Supprimer les messages qui s’adressent personnellement à l’utilisateur ou qui évoquent son téléphone.

Exemples à ne plus afficher :

  • « Ton iPhone XR dispose de… »
  • « Ton appareil est limité par… »
  • Messages qui rappellent inutilement les caractéristiques personnelles de l’appareil.

À la place, créer un véritable système de diagnostic neutre.

Exemples :

  • « Mémoire disponible insuffisante pour ce modèle. »
  • « Réduction recommandée du contexte. »
  • « Configuration GPU susceptible de limiter les performances. »
  • « Espace de stockage insuffisant pour ce téléchargement. »

Pal doit informer et conseiller sans produire de messages conversationnels inutiles sur l’appareil de l’utilisateur.

PARTIE V — MOTEUR D’INFÉRENCE ET PERFORMANCES

10. Optimisation générale

C’est l’un des chantiers les plus importants.

L’application doit exploiter intelligemment le CPU, le GPU et la mémoire.

Ne pas considérer systématiquement que l’accélération GPU est meilleure que le CPU.

Il faut mesurer les performances réelles.

Paramètres à examiner

  • Nombre de threads CPU.
  • Nombre de threads de traitement des lots.
  • Nombre de couches GPU.
  • Backend Metal.
  • Taille des lots.
  • Taille du contexte.
  • Cache KV.
  • Types K et V.
  • Flash Attention si compatible.
  • Quantification du modèle.
  • Allocations mémoire.
  • Préallocation des buffers.
  • Libération des ressources.
  • Temps de préremplissage du prompt.
  • Vitesse de génération.
  • Temps du premier token.

Problème constaté

Le mode Puissance a présenté des performances d’environ 10 tokens/s, avec des variations selon les modèles.

Un exemple de mesure visible dans une discussion :

  • 118 ms/token.
  • 8,5 tokens/s.
  • Premier token : 3,7 secondes.

Il faut déterminer précisément l’origine des ralentissements.

Ne pas se contenter de modifier arbitrairement le nombre de couches GPU.

Il faut comparer :

  1. CPU seul.
  2. Metal avec différentes configurations.
  3. Configuration hybride lorsque possible.
  4. Différents nombres de couches GPU.
  5. Différents nombres de threads.
  6. Différents contextes.

Mesurer les résultats sur plusieurs générations comparables.

11. Les trois profils de puissance

Les profils doivent réellement changer le comportement du moteur.

A. Économie

Objectif : diminuer la consommation de ressources.

Actions envisageables :

  • Réduire le nombre de threads.
  • Limiter les traitements parallèles.
  • Réduire le travail GPU lorsque cela est pertinent.
  • Utiliser un contexte plus modeste.
  • Réduire les allocations temporaires.
  • Décharger les ressources inutilisées.
  • Limiter les traitements d’arrière-plan.
  • Favoriser les modèles moins coûteux.

Important : iOS ne permet pas à une application tierce de forcer directement les fréquences CPU/GPU ni de contrôler intégralement la consommation électrique.

Le mode Économie doit donc appliquer les optimisations logicielles réellement possibles, sans prétendre contrôler le matériel.

B. Équilibré

Objectif : trouver le meilleur compromis.

  • Utilisation intelligente du CPU et du GPU.
  • Contexte adapté.
  • Threads adaptés.
  • Gestion raisonnable de la mémoire.
  • Bonne fluidité de l’interface.
  • Performances satisfaisantes.

C. Puissance

Objectif : exploiter les ressources disponibles.

  • Optimisation maximale du moteur.
  • Utilisation de Metal lorsqu’il est réellement avantageux.
  • Offload GPU adapté.
  • Paramètres de génération performants.
  • Gestion intelligente des threads.
  • Contexte adapté à la mémoire disponible.
  • Réduction des opérations inutiles.

Ce profil ne doit pas être ralenti par des limitations logicielles arbitraires provenant du profil Économie.

Règle fondamentale

Chaque profil doit avoir une configuration cohérente, identifiable et mesurable.

Le changement de profil doit réellement modifier les paramètres du moteur et non simplement changer une étiquette dans l’interface.

12. Objectif de capacité des modèles

État de référence déclaré : environ 1,7 milliard de paramètres utilisables dans les conditions actuelles du projet.

Objectif expérimental : 2,7 à 3 milliards de paramètres.

Cet objectif concerne les modèles réellement utilisables et stables, pas simplement les modèles qui arrivent à se charger.

Critères de réussite :

  • Chargement sans crash.
  • Génération stable.
  • Interface fluide.
  • Mémoire maîtrisée.
  • Pas de copies inutiles.
  • Temps de réponse acceptable.
  • Gestion correcte de la chauffe.
  • Pas de fermeture intempestive par iOS.

Tester différentes quantifications.

Un modèle 3B en Q4 peut être plus réaliste qu’un modèle de taille équivalente en Q8.

Ne pas sacrifier le contexte et la stabilité uniquement pour afficher un nombre de paramètres supérieur.

PARTIE VI — GESTION DES MODÈLES GGUF

13. Accès direct aux fichiers

Exigence fondamentale du projet.

Pal doit pouvoir utiliser les modèles présents dans deux emplacements :

  1. Sur mon iPhone.
  2. iCloud Drive.

Les modèles doivent être lus directement depuis leur emplacement d’origine.

Interdiction de copier systématiquement les modèles dans le dossier interne de Pal.

Pourquoi ?

  • Économiser le stockage.
  • Éviter les duplications.
  • Conserver une bibliothèque de modèles indépendante de Pal.
  • Permettre à l’utilisateur de gérer librement ses fichiers.

Gestion des autorisations

Utiliser les mécanismes iOS adaptés :

  • UIDocumentPicker.
  • Security-scoped URLs.
  • Bookmarks persistants lorsque nécessaires.
  • Vérification de l’accessibilité des fichiers.
  • Gestion des autorisations expirées.

Prévoir les situations où un fichier iCloud n’est pas encore téléchargé localement.

Ne jamais supposer qu’un fichier est disponible uniquement parce qu’il apparaît dans la liste.

Comportement attendu

  • Ajouter un GGUF depuis Fichiers.
  • Enregistrer sa référence d’accès.
  • Afficher sa disponibilité.
  • Charger le modèle directement.
  • Retrouver le modèle après fermeture de Pal.
  • Détecter un fichier déplacé ou supprimé.
  • Permettre de retirer le modèle de la bibliothèque sans supprimer le fichier original.

Aucun repli silencieux vers une copie interne.

14. Gestionnaire de téléchargement

C’est une priorité majeure de Pal 1.2.

Problème rencontré

Un modèle Qwen 3.5 0.8B a été téléchargé, mais Pal n’a pas réussi à l’ajouter à la bibliothèque.

Le téléchargement semblait avoir abouti, mais le modèle n’était pas correctement reconnu ou importé.

Il faut traiter séparément :

  • Le téléchargement.
  • La validation du fichier.
  • Son enregistrement.
  • Son indexation dans la bibliothèque.
  • Son chargement par llama.cpp.

Fonctionnalités attendues

  1. Recherche et téléchargement de modèles.
  2. Affichage de la progression réelle.
  3. Affichage de la taille téléchargée.
  4. Estimation du temps restant lorsque possible.
  5. Téléchargement en arrière-plan dans les limites iOS.
  6. Reprise après interruption lorsque le serveur le permet.
  7. Gestion des erreurs réseau.
  8. Détection des téléchargements incomplets.
  9. Vérification de la taille finale.
  10. Vérification de l’intégrité lorsque des sommes de contrôle sont disponibles.
  11. Vérification du format GGUF.
  12. Vérification des métadonnées utiles.
  13. Finalisation atomique du téléchargement.
  14. Ajout automatique à la bibliothèque.
  15. Possibilité d’ajouter manuellement le fichier depuis Fichiers.

Gestion des erreurs

Afficher des erreurs compréhensibles :

  • Téléchargement interrompu.
  • Espace insuffisant.
  • Fichier incomplet.
  • Format non reconnu.
  • Autorisation d’accès perdue.
  • Modèle incompatible.
  • Fichier inaccessible dans iCloud.
  • Métadonnées invalides.

Ne jamais déclarer un modèle installé uniquement parce que le téléchargement est terminé.

Architecture souhaitée

Séparer les responsabilités :

  • DownloadManager.
  • ModelValidator.
  • ModelLibraryManager.
  • ModelMetadataReader.
  • ModelLoader.

Les noms sont des propositions architecturales : vérifier d’abord les classes existantes pour éviter de créer des doublons.

PARTIE VII — RAISONNEMENT ET MULTIMODALITÉ

15. Gestion de la réflexion

Prévoir un contrôle permettant d’activer ou désactiver la réflexion.

Objectif : pouvoir utiliser un modèle de raisonnement sans lui imposer systématiquement son mode de réflexion.

Le comportement dépend du modèle.

À implémenter

  • Détection des capacités du modèle lorsque possible.
  • Configuration du format de prompt.
  • Activation de la réflexion.
  • Désactivation de la réflexion.
  • Respect des tokens et conventions propres au modèle.
  • Gestion des modèles qui ne disposent pas de mode réflexion.
  • Conservation du fonctionnement normal pour les modèles classiques.

Ne pas simplement supprimer du texte de sortie après génération en prétendant désactiver le raisonnement.

Il faut agir correctement sur le format de prompt et les paramètres compatibles.

16. Multimodalité et vision

Conserver et améliorer l’intégration multimodale.

Technologies envisagées :

  • llama.cpp.
  • MTMD.
  • mmproj.
  • OCR en solution complémentaire.

Fonctionnalités attendues

  • Sélection d’images depuis Photos.
  • Sélection de fichiers.
  • Analyse d’images avec modèle compatible.
  • Lecture de documents.
  • Gestion des modèles de vision.
  • Gestion des fichiers mmproj associés.
  • Gestion des incompatibilités.

Le fichier mmproj ne doit pas être confondu avec le modèle GGUF principal.

Lorsque le modèle possède une capacité multimodale native compatible, l’utiliser.

Lorsque ce n’est pas possible, l’OCR peut servir de solution de repli pour extraire le texte d’une image, sans prétendre effectuer une compréhension visuelle complète.

PARTIE VIII — INTELLIGENCE ÉVOLUTIVE

17. Skills / Compétences

Nous voulons que Pal puisse apprendre de nouvelles compétences au sens fonctionnel du terme.

Il ne s’agit pas de modifier les poids du modèle ou d’entraîner automatiquement le LLM.

Les Skills sont des instructions et procédures spécialisées que le modèle peut utiliser selon la tâche.

Format envisagé

Skills locaux en Markdown.

Exemple :

Skills/mathematiques/SKILL.md

Une compétence peut contenir :

  • Nom.
  • Description.
  • Domaine.
  • Instructions.
  • Méthodes de travail.
  • Exemples.
  • Sources recommandées.
  • Conditions d’utilisation.

Fonctionnement

  1. Identifier la tâche.
  2. Rechercher les compétences pertinentes.
  3. Sélectionner les Skills adaptés.
  4. Ajouter leurs instructions au contexte.
  5. Exécuter la tâche.
  6. Produire la réponse.
  7. Permettre à l’utilisateur d’ajouter ou modifier des compétences.

Compétences envisageables

  • Mathématiques.
  • Comptabilité SYSCOHADA.
  • Macroéconomie.
  • Statistiques.
  • Programmation.
  • Recherche documentaire.
  • Analyse de PDF.
  • Rédaction.
  • Traduction.
  • Résolution d’exercices.

Ne pas charger toutes les compétences simultanément : utiliser une sélection intelligente pour préserver la mémoire.

18. Mémoire locale

Prévoir une mémoire contrôlée par l’utilisateur.

Elle doit permettre :

  • De conserver certaines informations utiles.
  • De retrouver des éléments de conversations.
  • D’organiser les souvenirs.
  • De modifier ou supprimer des informations.
  • De contrôler ce qui est mémorisé.

Respecter la confidentialité.

Ne pas confondre mémoire conversationnelle, historique des discussions et connaissances du modèle.

19. Recherche Web

La recherche Web doit être sérieuse et fiable.

Pal doit pouvoir accéder à Internet lorsqu’une connexion est disponible.

Exigences

  • Recherche en ligne réelle.
  • Priorité aux sources fiables.
  • Plusieurs sources lorsque nécessaire.
  • Vérification des informations.
  • Liens vers les sources.
  • Citations associées aux affirmations.
  • Distinction entre faits et hypothèses.
  • Gestion des résultats contradictoires.
  • Date de publication lorsque pertinente.

Sources à privilégier

Selon le domaine :

  • Publications scientifiques.
  • Universités.
  • Organismes publics.
  • Documentation officielle.
  • Sites institutionnels.
  • Sources primaires.
  • Médias reconnus pour l’actualité.

Ne jamais inventer une recherche, une URL ou une citation.

Fonctionnement hors ligne

Lorsque la connexion est absente :

  • Les modèles locaux restent utilisables.
  • Les Skills locaux restent utilisables.
  • La mémoire locale reste utilisable.
  • Les documents locaux restent accessibles.

Ne jamais présenter une réponse générée sans Internet comme une recherche Web effectuée.

20. Documents et RAG

Prévoir un système de recherche documentaire.

Objectifs :

  • Lire des PDF.
  • Lire des fichiers texte.
  • Extraire le contenu.
  • Indexer les documents.
  • Retrouver des passages pertinents.
  • Fournir des réponses fondées sur les documents.
  • Citer les passages utilisés.

Le système doit distinguer les connaissances du modèle du contenu réellement retrouvé dans les documents.

21. Outils et extensions

Architecture modulaire à long terme.

Pal doit pouvoir accueillir de nouveaux outils sans modifier profondément son moteur principal.

Exemples :

  • Recherche Web.
  • Calculatrice.
  • Analyse de fichiers.
  • Gestion documentaire.
  • Résolution mathématique.
  • Recherche locale.
  • Gestion de données.
  • Automatisations autorisées.

Prévoir des permissions explicites et une validation des actions sensibles.

PARTIE IX — DIAGNOSTIC INTELLIGENT

22. Système d’analyse des ressources

Créer un ensemble de programmes qui récupèrent les données accessibles via les API iOS afin de produire des recommandations pertinentes.

Données à examiner

  • Espace de stockage disponible.
  • Taille des modèles.
  • Taille des fichiers mmproj.
  • État des téléchargements.
  • État des modèles.
  • Mémoire disponible ou pression mémoire lorsqu’elle est accessible.
  • Performances de génération.
  • Temps du premier token.
  • Tokens par seconde.
  • Erreurs de chargement.
  • Stabilité du moteur.
  • Consommation et chauffe uniquement dans les limites des informations exposées par iOS.

Ne pas prétendre accéder aux fréquences matérielles ou à des mesures énergétiques précises si iOS ne les expose pas.

Recommandations intelligentes

Exemples :

  • Réduire le contexte.
  • Utiliser une quantification plus légère.
  • Choisir un modèle plus petit.
  • Réduire les threads.
  • Modifier le nombre de couches GPU.
  • Fermer ou décharger un modèle inutilisé.
  • Libérer les caches.
  • Vérifier l’espace de stockage.
  • Éviter plusieurs modèles chargés simultanément.

Les recommandations doivent être basées sur des observations réelles.

Confidentialité

  • Analyse locale par défaut.
  • Pas de collecte cachée.
  • Pas de transmission automatique de données personnelles.
  • Explications compréhensibles.
  • Contrôle utilisateur.

L’utilisateur doit pouvoir :

  • Écrire son propre prompt.
  • Le modifier.

PARTIE XIII — RÈGLES DE COLLABORATION AVEC CLAUDE

28. Instructions permanentes

Claude doit respecter les règles suivantes pendant toute sa participation au projet.

Règle 1 — Ne pas dégrader l’existant

Ne jamais supprimer une fonctionnalité existante simplement pour faciliter une modification.

Avant de modifier un fichier :

  • Lire son contenu.
  • Comprendre son rôle.
  • Identifier ses dépendances.
  • Identifier les fonctions qui l’utilisent.
  • Prévoir les conséquences de la modification.

Règle 2 — Éviter les réécritures inutiles

Privilégier les modifications ciblées.

Ne pas remplacer un fichier complet lorsqu’une petite modification suffit.

Ne pas multiplier les classes qui font la même chose.

Règle 3 — Être honnête sur les résultats

Ne jamais affirmer qu’une fonctionnalité est terminée sans preuve.

Signaler explicitement :

  • Les modifications effectuées.
  • Les fichiers modifiés.
  • Les fichiers créés.
  • Les problèmes identifiés.
  • Les tests effectués.
  • Les tests impossibles.
  • Les risques restants.

Règle 4 — Respecter les contraintes iOS

Ne pas proposer de mécanismes qui nécessitent des permissions privées ou des API non autorisées.

Ne pas prétendre contrôler les fréquences CPU/GPU.

Ne pas prétendre disposer d’une mémoire illimitée.

Ne pas contourner les restrictions iOS sans expliquer les conséquences.

Règle 5 — Travailler avec les vrais fichiers

Les sources du projet sont prioritaires sur les suppositions.

Toujours vérifier les noms, les structures et les signatures existantes.

Ne pas inventer des chemins de fichiers.

Ne pas produire de code isolé sans expliquer son intégration.

Règle 6 — Livrer de manière exploitable

Lorsque des modifications sont réalisées :

  • Fournir les fichiers complets lorsque nécessaire.
  • Fournir les chemins exacts.
  • Indiquer les fichiers à remplacer.
  • Indiquer les nouveaux fichiers.
  • Indiquer les modifications du projet XcodeGen.
  • Préserver le workflow de compilation.
  • Fournir les instructions de compilation.
  • Signaler les tests non réalisés.

Si une limite de longueur ou de génération empêche une livraison complète, le signaler au lieu de prétendre que tout est terminé.

Règle 7 — Ne pas oublier la vision globale

Chaque nouvelle fonction doit être conçue pour s’intégrer dans l’architecture future de Pal.

Éviter les solutions temporaires qui rendraient les prochaines évolutions plus difficiles.
